# Enterprise Reporting TanStack — Application Context Specification

> Machine-readable spec of `enterprise_reporting_tanstack`: architecture,
> conventions, data layer, server functions, auth, RBAC, NL query, reports,
> charts, dashboards, background jobs — and how EML models reach it through the
> `eml` CLI's `enterprise-reporting` target. Written for language models.

- **Spec version**: 2.0.0 · **Updated**: 2026-09-07
- **Location in this repository**: `enterprise_reporting_tanstack/`
- **Runtime**: Bun ≥ 1.3.0. `node` is not supported for development
- **Dev server**: `bun --bun vite dev` → http://localhost:4050
- **Sibling spec**: `llms-full.txt` describes APPWITHAI, the *other* consumer of
  the same EML models. Read that one for the language itself; read this one for
  the reporting platform. Neither is a substitute for the other.

This file supersedes `enterprise_reporting_tanstack/llmtext/llms-full.txt`,
which describes a MariaDB config database and a SQLite fallback. Neither exists
in the running system. Where the two disagree, this file is right and that one
is a snapshot of an architecture that has since been migrated.

---

## 0. The one idea

Enterprise Reporting TanStack is a full-stack, multi-datasource analytics
platform built on TanStack Start. **One** application connects to **many**
external databases, runs natural-language and hand-written SQL against them,
enforces two layers of access control, and renders the results as tables,
charts, dashboards and scheduled exports.

```
external DBs (pg | mysql | mssql)   ← the user's data, connected at runtime
        ↑
        │  connection-manager, per-source pool, AES-256-GCM encrypted config
        │
config DB (PostgreSQL: enterprise_config)   ← users, roles, data sources,
        │                                      saved queries, reports, charts,
        │                                      dashboards, jobs, audit, logs
        ├── NL Query    CopilotKit → Mastra → llama.cpp → SQL → AST validation
        ├── RBAC        system roles  +  per-datasource roles and entity grants
        ├── Render      Recharts / ECharts + TanStack Table
        ├── Export      CSV · Excel (exceljs) · PDF (jspdf + autotable)
        └── Jobs        Trigger.dev, or a built-in Bun cron loop as fallback
```

Four properties matter above all, and most mistakes in this codebase are a
violation of one of them:

1. **Two databases, different jobs.** The application's own config database is
   **PostgreSQL only** (`enterprise_config`). Every data source a user connects
   is a *separate external* database queried at runtime. Never mix the two: the
   config DB has a typed Kysely `Database` interface; a data source is
   `Kysely<any>` because its schema is not knowable at build time.
2. **Server functions, not a REST API** — mostly. Backend logic lives in
   TanStack Start server functions under `src/server-fns/`. There is also a
   real set of API routes under `src/routes/api/` for things a server function
   cannot be: webhooks, streaming, CopilotKit, and anything an external caller
   hits. Both exist on purpose; see §5.
3. **`.inputValidator()`, never `.validator()`.** This is not a style
   preference. See §5.
4. **Server-side pagination is mandatory.** Every data query applies
   `LIMIT`/`OFFSET` at the database. Fetching a table and paginating in the
   browser is a defect, not a shortcut — the data sources are other people's
   production databases.

## 4. The database layer

### 4a. Config database — PostgreSQL

`src/lib/db/kysely-db.ts`, re-exported by `src/lib/db/config.ts`:

```ts
import { getDb } from "@/lib/db/config";
const rows = await getDb().selectFrom("report_definitions").selectAll().execute();
```

- Connection from `DATABASE_URL`, else assembled from
  `POSTGRES_HOST/PORT/DB/USER/PASSWORD` (or `PGHOST`/`PGPORT`/…), defaulting to
  `localhost:5432/enterprise_config` as user `enterprise`.
- **`getDb()` is synchronous.** On the first call it runs `bootstrapSchema()`
  from `src/lib/db/bootstrap.ts`, which is idempotent (`CREATE TABLE IF NOT
  EXISTS`) and therefore safe on every boot.
- The `Database` interface in `kysely-db.ts` is the authoritative type for the
  config DB. **Add a table there and in `bootstrap.ts` in the same change.**

The 27 tables the `Database` interface declares:

```
users  roles  user_roles  resource_permissions
data_sources  saved_queries
report_definitions  chart_definitions
dashboard_layouts  dashboard_widgets
job_definitions  job_executions
audit_log  logs  email_templates
filter_definitions  report_filters  chart_filters
ds_roles  ds_user_roles  ds_entity_permissions
schema_table_instructions  schema_field_instructions
nl_query_context  nl_query_role_stats  nl_query_feedback
help_articles
```

**Known drift, stated plainly.** `bootstrapSchema()` creates 36 tables. Nine of
them are not declared in the `Database` interface:

```
adk_intents  ds_schema_cache  generated_report_artifacts
metadata_entity_field  metadata_entity_header
monitoring_executions  monitoring_rules
nl_report_definitions  notifications
```

They exist, they are queried through `getDb()` (`monitoring-repository.ts` is
the clearest case), and Kysely cannot type-check any of it. This is the rule in
§4a being broken, not an alternative pattern to copy: a new table goes in both
places, and closing this gap for an existing one is a welcome change.

### 4b. External data sources

`src/lib/db/connection-manager.ts`:

```ts
import { getConnection } from "@/lib/db/connection-manager";
const kysely = await getConnection(dataSource);   // Kysely<any>
```

- `client_type` is one of `pg`, `mysql`, `mssql`.
- Connection configs are stored **AES-256-GCM encrypted** in
  `data_sources.connection_config` and decrypted through
  `src/lib/security/encryption.ts` with `ENCRYPTION_KEY` (64 hex characters).
- Connections are pooled per data source id and health-checked before reuse.
  `closeConnection(id)` and `closeAllConnections()` release them.
- **Hostnames are resolved to IPv4 explicitly** (`resolveIPv4`). Docker's DNS
  returns IPv6 first and that path fails against Neon pooler endpoints. If you
  touch this, keep `ssl.servername` set — dropping it breaks TLS verification
  against hosts whose certificate is issued for the name, not the address.

### 4c. Knowledge graph

A separate PostgreSQL database, `ers_knowledge`, running Apache AGE. Its own
pool lives in `src/lib/graph/client.ts` (`GRAPH_DATABASE_URL`, graph name
`knowledge_graph`), with `cypher()`, `cypherWrite()` and `graphSql()` helpers.
It holds schema structure used as NL-query context.

## 5. Server functions — the conventions that bite

Server functions live in `src/server-fns/`.

### The one that is not negotiable

```ts
// CORRECT
export const listReportsFn = createServerFn({ method: "GET" })
  .inputValidator((data: { page?: number }) => data)
  .handler(async ({ data }) => { /* ... */ });

// A client call MUST wrap the input when an input validator is declared:
const result = await listReportsFn({ data: { page: 0 } });

// With no input validator, no wrapper:
export const getMeFn = createServerFn({ method: "GET" }).handler(async () => { /* ... */ });
await getMeFn();
```

**`.inputValidator()`, never `.validator()`.** The TanStack Start Vite plugin
recognises only `.inputValidator()`; it preserves any other method name verbatim
in the client bundle. `.validator()` therefore type-checks, builds cleanly, and
crashes at runtime with no compile-time signal. If a server function throws on
its first call in the browser and the backend never saw the request, this is why.

### Error handling

Newer server functions wrap their body in `withErrorHandler()` from
`src/lib/server-fns/with-error-handler.ts`, which audit-logs the failure and
normalises the error into a `ServerFunctionError` subclass:

| Class | HTTP |
|---|---|
| `ValidationError` | 422 |
| `UnauthorizedError` | 401 |
| `NotFoundError` | 404 |

Older ones return `{ success: boolean, data?: T, error?: string }` directly.
Both shapes are live. Prefer `withErrorHandler` in new code; do not rewrite a
working caller's contract in passing.

### API routes

Routes under `src/routes/api/` use the `server.handlers` pattern:

```ts
export const Route = createFileRoute("/api/reports/$id")({
  server: {
    handlers: {
      GET: async ({ request, params }) => json({ /* ... */ }, { status: 200 }),
    },
  },
});
```

They exist for what a server function is not: `api/copilotkit/$` (the AI
sidebar's transport), `api/voice/ws` (a socket), `api/health`, the streaming and
export endpoints, and everything under `share/` that an unauthenticated viewer
reaches. `src/routeTree.gen.ts` is generated — never edit it by hand.

## 6. Authentication

- A JWT signed with `AUTH_SECRET`, carried in a `session_token` **HttpOnly**
  cookie.
- `verifySession(token)` in `src/lib/auth/session.ts` returns `Session | null`;
  `createSession(user)` issues one; `authenticateUser()` checks credentials.
- **In a server function:** `import { requireAuth } from "@/lib/auth/middleware"`,
  then `const session = await requireAuth()`.
- **In an API route handler:** extract the cookie yourself and call
  `verifySession(token)` — there is no request context to read it from.
- `src/routes/_authed.tsx` runs the check in `beforeLoad` and injects
  `{ session }` into route context, read with `Route.useRouteContext()`.
  It redirects to `/login` when there is no valid session.

`_authed` is a **pathless layout route**. Its children are addressed without it:
the file is `src/routes/_authed/reports/$id.tsx`, `createFileRoute` is keyed
`"/_authed/reports/$id"`, and a `<Link>` goes `to="/reports/$id"`. Putting
`_authed` in the link is the mistake to not make.

### Default credentials

`bootstrapSchema()` seeds these **only when no users exist**:

- `admin@admin.com` / `admin` — full administrator
- `nlquery@nlquery.com` / `nlquery` — NL query role only

`bun run db:seed` adds `analyst@example.com` / `analyst123` and a sample Sakila
data source.

## 7. RBAC — two layers

Both layers live in the config database, and a request passes through both.

### Layer 1 — system RBAC

`roles` + `user_roles`, with permission strings shaped `resource:action`:
`data_source:view`, `nl_query:*`, `*:*`. Helpers in
`src/lib/permissions/permissions.ts`:

```ts
getUserPermissions(userId)
isAdmin(userId)
hasPermission(permissions, resource, action)
hasResourceAccess(userId, resourceType, resourceId, action)
filterAccessibleResources(userId, resourceType, rows)
canCreateResource(...)  canDeleteResource(...)
requirePermission(...)
```

`resource_permissions` grants access to an individual resource — one report, one
chart — beside the role-level grant.

### Layer 2 — data-source RBAC

`ds_roles`, `ds_user_roles`, `ds_entity_permissions`: per-table and per-column
access, per data source, per role. Helpers in
`src/lib/permissions/ds-rbac.ts` — `checkEntityAccess`,
`getUserAccessibleEntities`, and the CRUD around roles and grants.

**This is the layer that makes generated SQL safe.** Every query bound for a
data source is parsed by `src/lib/mastra/sql-parser.ts`
(`extractEntitiesFromSql`, `validateSqlTokens`, `validateSqlAccess`) and the
tables it touches are checked against `ds_entity_permissions` *before* it
executes. A natural-language question that compiles to valid SQL over a table
the asker may not read is refused at that step, not at the database.

## 8. NL Query pipeline

```
/_authed/nl-query  →  CopilotKit sidebar  →  /api/copilotkit
                   →  Mastra AI server (MASTRA_URL, default :4111)
                   →  llama.cpp (OpenAI-compatible)
                   →  pgvector RAG
```

`src/lib/mastra/nl-query-pipeline.ts` is the full path, in order:

1. **Fetch schema context (RAG)** for the data source.
2. **Generate SQL** from the question — `buildSqlGenerationPrompt()` assembles
   the prompt; `src/lib/nlquery/mastra-connector.ts` or `llama-translator.ts`
   calls the model.
3. **Parse and validate** the SQL with the AST parser.
4. **Check entity-level RBAC** (§7, layer 2).
5. **Execute** only if access was granted.
6. **Return** rows with metadata.

The RAG store (`src/lib/mastra/rag-store.ts`) keeps `nl_query_embeddings` and
`nl_schema_embeddings` pgvector tables in the user's PostgreSQL database:
`findSimilarQueries`, `findRelevantSchema`, `storeQueryEmbedding`,
`storeSchemaEmbeddings`, `buildRagContext`,
`introspectAndStoreSchemaEmbeddings`.

Two operational facts worth stating before anyone debugs this:

- **Embedding dimension is 384.** Changing it means re-ingesting every
  embedding — the tables are dimensioned, not adaptive.
- **The embedding server is optional.** With none reachable, `generateEmbedding`
  falls back to hash-based vectors. Retrieval keeps working and gets worse; it
  does not fail loudly. A sudden drop in answer quality with no errors in the
  log is this.

`src/lib/adk/` is an agent/tool-orchestration variant of the same pipeline
against the same Mastra server, with an intent classifier and a tool registry.

## 9. Reports, charts, dashboards

All three are **definitions in the config DB, executed on demand** — none of
them stores result data.

| Concept | Table | Points at |
|---|---|---|
| Report | `report_definitions` | `saved_query_id`, plus `column_config`, `filter_config`, `sort_config`, `pagination_config`, `export_formats`, `filename_template`, `color_theme` (all JSON) |
| Chart | `chart_definitions` | `saved_query_id`, plus `chart_type`, `chart_config`, `data_mapping`, `refresh_interval`, `color_theme` |
| Dashboard | `dashboard_layouts` + `dashboard_widgets` | a widget carries `widget_type` and either `report_id` or `chart_id`, plus `position_config` |
| Filters | `filter_definitions`, joined via `report_filters` / `chart_filters` | reusable filter definitions bound to a report or chart |

All three carry `is_public`, and soft deletion (`is_deleted`, `deleted_at`,
`deleted_by`) rather than a hard `DELETE`. `is_public` is what the
unauthenticated `share/` routes serve — treat it as a publication decision, not
a convenience flag.

Server functions: `src/server-fns/reports.ts`, `charts.ts`, `dashboards.ts`,
`filters.ts`. API routes mirror them under `src/routes/api/` for the endpoints
that stream or export (`/api/reports/$id/data`, `/api/reports/$id/export`,
`/api/charts/$id/data`).

Export goes through `src/lib/export/`: CSV, Excel via `exceljs`, PDF via
`jspdf` + `jspdf-autotable`.

`src/server-fns/admin-builder.ts` is the AI-assisted side: a CopilotKit surface
that builds a report or chart definition from a natural-language description,
using the same NL→SQL path as §8.

## 10. Background jobs — Trigger.dev, not BullMQ

Configured in `trigger.config.ts` (project `enterprise-reporting`, tasks
discovered under `./src/lib/jobs`).

| Task id | Defined in | Work in |
|---|---|---|
| `report:generate` | `src/lib/jobs/trigger-tasks.ts` | `workers/report-worker.ts` |
| `data:export` | same | `workers/export-worker.ts` |
| `email:batch` | same | `workers/email-batch-worker.ts` |
| `scheduled:refresh` | same | — |
| `monitoring:evaluate` | same | `workers/monitoring-worker.ts` |

- Enqueue through `src/lib/jobs/trigger-queue.ts`.
- `src/lib/jobs/worker-runner.ts` picks the backend: **Trigger.dev when
  `TRIGGER_API_URL` is set**, otherwise it starts the built-in on-premise cron
  runner (`src/lib/monitoring/monitoring-scheduler.ts`) — a pure-Bun interval
  loop that polls `monitoring_rules` every minute. The fallback is not a stub;
  it is how the product runs without a Trigger.dev deployment.
- Schedules and history live in `job_definitions` (`schedule_cron`,
  `job_type`, `target_id`, `notification_config`) and `job_executions`.
- **`src/lib/queue/` is dead.** BullMQ + ioredis, neither a dependency, nothing
  imports it. Comments elsewhere mentioning BullMQ or Bull Board are migration
  leftovers.

## 11. Other subsystems

- **DuckDB WASM** (`src/lib/duckdb/`, `DuckDBProvider` in the root layout):
  in-browser SQL over an already-fetched result set, gated by
  `NEXT_PUBLIC_WASM_ENABLED`. Progressive loading in `src/lib/wasm/`.
- **Metadata layer** (`src/lib/metadata/`): entity and field definitions, sync
  from live data-source schemas, and metadata-level permissions. Surfaced at
  `/_authed/metadata` and `/api/metadata/*`.
- **Schema instructions** (`schema_table_instructions`,
  `schema_field_instructions`): human-written notes about what a table or column
  *means*, fed to the LLM as context. This is the highest-leverage thing an
  administrator can fill in for NL query quality.
- **OpenKB** (`src/lib/openkb/`): knowledge-base client and embedding service
  for help content; `help_articles` and `/api/help/articles`.
- **Logging** (`src/lib/logging/`): Pino, with logs also persisted to the config
  DB `logs` table and browsable at `/_authed/logs` and `/_authed/system-logs`.
- **TanStack DB** (`src/lib/tanstack-db/collections.ts`): local in-memory
  `@tanstack/db` collections, **no server sync configured** —
  `activeFiltersCollection`, `chartDraftCollection`, `dashboardStateCollection`,
  `queryHistoryCollection`, `reportsCollection`, `chartsCollection`,
  `dashboardsCollection`.

## 14. EML in this repository

There are **two** copies of the EML language system, and they are not the same
file:

| Copy | Definition file | Role |
|---|---|---|
| `language/` at the **root of the combined repository** | `appwithai-language.json` | Canonical. Newer checker, more directives documented, and the only copy that carries all three generator targets |
| `enterprise_reporting_tanstack/language/` | `erdwithai-language.json` | The reporting project's own older copy. Same language, renamed, with an `enterprise-reporting` generator target and no `tanstack-nestjs` one |

**Prefer the root copy.** When they disagree about a directive's meaning, the
root copy is the language.

### Generating entities for this platform

```bash
bun language/cli/eml.ts generate -i model.eml.mmd -o ./out --stack enterprise-reporting
```

Per entity in the model it writes:

```
out/
  src/server-fns/<entity>.ts               list/get/create/update/delete
  src/routes/_authed/<entity>/index.tsx    list page  (TanStack Table + shadcn/ui)
  src/routes/_authed/<entity>/$id.tsx      detail / edit page
  src/lib/db/migrations/<ts>_create_tables.ts   Kysely migration, PostgreSQL DDL
  KYSELY_TYPES.md                          snippet for the Database interface
  README.md                                the integration steps
```

**It is not a standalone application, on purpose.** This repository already
holds auth, both RBAC layers, the encrypted connection manager, the NL-query
pipeline, the job runner and the UI shell. A generated copy of any of them would
be a fork of a moving part. So the target emits only what a new entity needs and
leaves the rest as integration:

1. Copy the files to the paths shown.
2. Paste `KYSELY_TYPES.md` into the `Database` interface in
   `src/lib/db/kysely-db.ts`.
3. Add the `CREATE TABLE` statements to `bootstrapSchema()` in
   `src/lib/db/bootstrap.ts` — §4a — or apply the migration. Full reset:
   `bun scripts/rebuild-db.ts`.
4. Add navigation links under `src/components/layout/`.
5. **Add permission checks.** The generated handlers call `requireAuth()`, which
   establishes *who* is calling. They do not call `requirePermission()`, because
   `%%rbac` is not compiled by this target — deciding what a role may do is a
   decision, and a generated guess at it would be an access-control decision
   nobody made.

### What the target compiles, and what it does not

| EML level | `enterprise-reporting` |
|---|---|
| core — entities, fields, enums, indexes | Compiled: tables, Zod schemas, form fields, table columns |
| rules | Emitted as GoRules JDM under `rules/`, **not wired up** |
| workflows — hooks, state machines, sagas | **Not compiled** |
| access — `%%rbac` | **Not compiled** — step 5 above |
| help | Field labels only |

Write the model in full anyway. The behaviour this target skips is still what
the checker validates, what the viewers render, and what the `tanstack-nestjs`
target compiles from the very same file.

### Conventions the generated code follows

They are the conventions of §5, §6 and §4a, applied without exception:
`.inputValidator()`; `{ data: … }` on every call; `requireAuth()` at the top of
every handler; `LIMIT`/`OFFSET` at the database; `getDb` from
`@/lib/db/config`; PostgreSQL DDL with double-quoted identifiers
(`TIMESTAMPTZ`, `BOOLEAN`, `JSONB`, `NUMERIC(10,2)`, `gen_random_uuid()`); an
`FK` attribute emitted as `UUID` so the constraint can actually be added; and
`updated_at` set by the update handler, because PostgreSQL has no
`ON UPDATE CURRENT_TIMESTAMP`.

## 14a. Running beside a generated application

`./start.sh` at the repository root brings the two products up together on one
origin, with the reporting platform already loaded with the generated
application's data:

```
http://localhost/app      the application generated from an EML model
http://localhost/report   this platform, holding that application's schema,
                          reports, charts and dashboard
```

### What start.sh does before Docker

1. Checks the model. A model with errors stops here.
2. Generates the application into `common/.runtime/app` (`--stack tanstack-nestjs`).
3. Runs `common/build/subpath-overlay.ts` over the generated front end, putting
   it on `/app`.
4. Runs `common/build/reporting-pack.ts` over the model, deriving the pack into
   `common/.runtime/pack/reporting-pack.json`.
5. Generates the secrets into `common/.runtime/.env` on first run, and never
   again — regenerating `ENCRYPTION_KEY` would leave every stored connection
   config undecryptable, and that failure reads as a broken data source rather
   than a rotated key.
6. `docker compose up -d --build`.

### The two profiles

| | Databases | Why |
|---|---|---|
| `demo` (default) | one Apache AGE PostgreSQL 16 holding three databases: the application's, `enterprise_config`, `ers_knowledge` | one container, one image |
| `prod` | two servers — pgvector on PostgreSQL 18 for the application, Apache AGE on 16 for this platform | each application gets the image it actually asks for |

Under both, **this platform's configuration never shares a database with the
application it reports on.** Regenerating the application drops and recreates its
tables; the reports have to survive that.

### Serving at /report

Neither application was written to live anywhere but the root of a host, so both
are *built* for their prefix rather than proxied into it. Three things have to
agree — the bundler's `base`, the router's `basepath`, and the hand-written
static wrapper's URL-to-file mapping — and `common/build/subpath-overlay.ts`
patches all three. It is applied to a copy: the generated application's output,
and this project's source inside its image at build time. Nothing checked in
under `enterprise_reporting_tanstack/` is modified.

**nginx deliberately does not strip the prefix.** Stripping would satisfy the
static wrapper for free and then break the router: the server would receive
`/dashboard` while every link the router writes says `/report/dashboard`.

### What the seeder loads

`common/seed/seed-reporting.ts` runs once per `up`, and is idempotent by name:

1. Waits for both databases **and for the application's `bus_` tables** — an
   empty application database means "not migrated yet", and introspecting then
   would cache a schema with no tables in it.
2. Registers the application's database as a data source, its connection config
   encrypted through this project's own `encrypt()`.
3. `introspectAndCacheSchema()` — the same call the data-source screens make, so
   the cached shape is the one the readers expect.
4. Writes the pack: saved queries, report definitions, chart definitions, the
   dashboard and its widgets, all owned by the bootstrap administrator.

It is built from this project's own source rather than a bare Bun image, so it
uses this project's `getDb`, `encrypt` and `introspectAndCacheSchema` rather than
a second implementation of each. A seeder with its own encryption would drift
from the reader, and the failure would be a data source that exists and cannot
be opened.

### Where the reports come from

Two sources, and the distinction matters when explaining what is in the
platform:

- **Derived** from structure by `common/build/reporting-pack.ts`: a register per
  entity, a breakdown per `%%enum`-bound column, created-per-month, a lifecycle
  report per state machine (in the diagram's order, zeroes included), measures
  over numeric columns, and children-per-parent for every `oneToMany`.
- **Authored** in the model as `%%report` directives — a question the
  application's users actually ask, written as the SQL that answers it. These
  are listed ahead of the derived ones and take the top tiles of the dashboard.

The derived set describes the shape of the data and nothing about the business
running on it. `%%report` is where the domain knowledge lives. See
`llmdetailed.txt` §10.5.1 for how a model author is asked to produce them.

## 15. Worked example — adding an entity by hand

The generator does this for you; do it this way when writing one directly.

**Step 1 — schema.** Add the table to `bootstrapSchema()` in
`src/lib/db/bootstrap.ts` *and* the interface to `Database` in
`src/lib/db/kysely-db.ts`. Same change, both files.

**Step 2 — server functions.** `src/server-fns/<entity>.ts`:

```ts
import { createServerFn } from "@tanstack/react-start";
import { z } from "zod";
import { requireAuth } from "@/lib/auth/middleware";
import { getDb } from "@/lib/db/config";

const InputSchema = z.object({ name: z.string(), notes: z.string().optional() });

export const listWidgetsFn = createServerFn({ method: "GET" })
  .inputValidator((input: { page?: number; pageSize?: number }) => input)
  .handler(async ({ data }) => {
    await requireAuth();
    const page = data.page ?? 0;
    const pageSize = Math.min(data.pageSize ?? 50, 1000);
    const [items, countRow] = await Promise.all([
      getDb().selectFrom("widgets").selectAll()
        .orderBy("created_at", "desc").limit(pageSize).offset(page * pageSize).execute(),
      getDb().selectFrom("widgets")
        .select((eb) => eb.fn.countAll().as("count")).executeTakeFirstOrThrow(),
    ]);
    return { items, total: Number(countRow.count), page, pageSize };
  });

export const createWidgetFn = createServerFn({ method: "POST" })
  .inputValidator((input: z.infer<typeof InputSchema>) => InputSchema.parse(input))
  .handler(async ({ data }) => {
    await requireAuth();
    const id = crypto.randomUUID();
    await getDb().insertInto("widgets").values({ id, ...data }).execute();
    return { id };
  });
```

**Step 3 — routes.** `src/routes/_authed/widgets/index.tsx` and `$id.tsx`, keyed
`createFileRoute("/_authed/widgets/")`, linked as `to="/widgets/$id"`.

**Step 4 — permissions.** Add `widget:view` / `widget:edit` (or whatever the
resource is called) to the roles that should hold them, and call
`requirePermission()` where the check belongs.

**Step 5 — navigation.** Add the entry under `src/components/layout/`.

## 16. Code conventions

- **Biome**, not ESLint or Prettier. `bun run precommit` is the gate.
- Imports use the `@/` alias for `src/`. Server-only modules stay out of
  components.
- `routeTree.gen.ts` is generated. Biome does not format it and neither do you.
- Route files are lower-case kebab; components are PascalCase.
- Styling is Tailwind + shadcn/ui. Reach for an existing `components/ui/`
  primitive before writing a new one.
- Every list query paginates at the database (§0.4).
- Never log a credential, a connection config, or a data-source row's decrypted
  contents.

## 17. Stale documentation — what not to trust

Most files under `enterprise_reporting_tanstack/docs/` predate the migrations to
PostgreSQL and Trigger.dev and describe SQLite/MariaDB, BullMQ + Redis, Bull
Board, and OpenAI-based NL query. **`docs/README.md` and `CLAUDE.md` are
current; verify anything else in `docs/` against source before trusting it.**
`llmtext/llms-full.txt` in that folder is superseded by this file.

The same applies to the compose files: **`docker-compose.yml` is current**
(PostgreSQL via `apache/age:PG16`, `DATABASE_URL` / `GRAPH_DATABASE_URL`), while
`docker-compose.dev.yml`, `docker-compose.local.yml` and
`docker-compose.remote.yml` still start a MariaDB container and pass `MARIADB_*`
variables the application ignores entirely.

## 18. Common pitfalls

| Symptom | Cause |
|---|---|
| A server function crashes on its first call and the backend never saw it | `.validator()` instead of `.inputValidator()` (§5) |
| `data is undefined` inside a handler | The client called it without the `{ data: … }` wrapper |
| A `<Link>` 404s | `_authed` was included in the `to` — it is a pathless layout (§6) |
| A data source connects locally and fails in Docker | IPv6 first from Docker DNS; `resolveIPv4` exists for this (§4b) |
| NL answers quietly get worse, no errors | No embedding server; hash-based fallback vectors (§8) |
| A new table type-checks nowhere | Added to `bootstrap.ts` but not to the `Database` interface (§4a) |
| Scheduled work never runs | `TRIGGER_API_URL` unset and the worker process not started (§10) |
| `bun run typecheck` clean, production build fails | An import only the build resolves — run `bun run build:check` |
| Anything in `docs/` contradicts this file | §17 |

## 19. Rules for answering questions about this system

1. **Never say MariaDB, SQLite, BullMQ, Redis or Bull Board describe the running
   system.** They appear in the tree; none of them runs. Say so, and point at
   §17 rather than hedging.
2. **Do not invent a REST endpoint.** Backend logic is a server function unless
   it is one of the API routes listed in §5, and those are enumerable — check
   `src/routes/api/` before claiming an endpoint exists.
3. **Quote the `.inputValidator()` rule whenever a server function is written.**
   It is the single most expensive mistake available in this codebase, because
   it produces no compile-time signal.
4. **Keep the two databases apart.** Config DB: typed, PostgreSQL, `getDb()`.
   Data source: `Kysely<any>`, `getConnection(dataSource)`, and never trusted
   without the §7 access check.
5. **When asked what an EML model produces here, say what it does not.**
   Workflows and `%%rbac` are not compiled by the `enterprise-reporting` target
   (§14). A model author who believes their access rules were generated has an
   unguarded application and no reason to look.
6. **Point at the sibling spec for the language.** `llms-full.txt` covers EML and
   the APPWITHAI generator in full; this file covers only how a model reaches
   the reporting platform.
